# RFC-0002: AUGUR Threat Advisory Engine

- **Status:** Draft
- **Priority:** Low
- **Date:** 2026-03-31
- **Authors:** Security Intelligence Group (SIG)
- **Depends on:** RFC-0001 (CITADEL Governance Protocol)

---

## Summary

AUGUR is the threat-advisory subsystem referenced at Gate 4 of the MARSHAL evaluation engine
(RFC-0001 §3.2). This RFC fully specifies AUGUR's advisory lifecycle, severity model, authoring
API, and the evaluation contract MARSHAL relies on. It also resolves RFC-0001 Open Question 5
(advisory clearance lifecycle) and partially addresses Open Question 2 (VIGIL_DEEP anomaly SLA).

---

## Motivation

RFC-0001 defines that MARSHAL Gate 4 checks "whether the AUGUR (BEACON) advisory engine holds a
CRITICAL advisory that blocks this action type for this project." However, RFC-0001 does not
specify:

- What an advisory consists of (schema, fields, scope).
- How advisories are created, reviewed, and cleared.
- How MARSHAL decides whether a specific advisory blocks a specific action.
- What happens when a blocking advisory expires vs. is manually resolved.
- How VIGIL surfaces active advisories in its health state.

Without this specification, Gate 4 is a stub: it cannot be implemented deterministically, and
operators have no way to manage the advisory backlog.

---

## Design

### 4.1 Advisory Schema

An AUGUR advisory is a structured threat signal that can block one or more action types for one
or more projects. Advisories are stored in `augur.advisories` and referenced by MARSHAL at
Gate 4.

```json
{
  "advisory_id": "uuid",
  "title": "Unpatched CVE-2026-XXXX in TLS library affects all API connectors",
  "description": "CVE-2026-XXXX allows a remote attacker to perform a MitM attack against ...",
  "severity": "CRITICAL",
  "source": "sig_manual",
  "cve_refs": ["CVE-2026-XXXX"],
  "affects": {
    "projects": ["*"],
    "action_types": ["deploy_change", "config_update"]
  },
  "status": "ACTIVE",
  "created_by": 42,
  "created_at": "2026-03-31T09:00:00Z",
  "expires_at": "2026-04-07T09:00:00Z",
  "resolved_at": null,
  "resolved_by": null,
  "resolution_note": null,
  "worm_entry_id": "uuid-of-worm-log-entry"
}
```

**Field constraints:**

| Field | Type | Constraint |
|-------|------|-----------|
| `advisory_id` | UUID | Auto-generated, immutable |
| `severity` | enum | `INFO` \| `HIGH` \| `CRITICAL` |
| `source` | enum | `sig_manual` \| `vigil_deep` \| `api_import` |
| `affects.projects` | string array | Project IDs or `"*"` (all projects) |
| `affects.action_types` | string array | Action type strings from MARSHAL vocabulary, or `"*"` |
| `status` | enum | `DRAFT` \| `ACTIVE` \| `EXPIRED` \| `RESOLVED` |
| `expires_at` | ISO 8601 | Optional; advisory auto-expires at this time if not resolved |
| `worm_entry_id` | UUID | Written on every status transition (creation, activation, resolution) |

An advisory in `DRAFT` status is visible to admins but does not block MARSHAL. Only `ACTIVE`
advisories are evaluated at Gate 4.

### 4.2 Advisory Lifecycle

```
                       ┌─────────────────────────────────────────────────┐
                       │                                                 │
  POST /advisories  ───►  DRAFT ──── activate() ────►  ACTIVE           │
                       │               │                   │             │
                       │               │ discard()         │ expires_at  │
                       │               ▼                   │ reached     │
                       │           (deleted)               ▼             │
                       │                               EXPIRED           │
                       │                                   │             │
                       │                   resolve()       │  resolve()  │
                       │                   ◄───────────────┘             │
                       │                   │                             │
                       │                   ▼                             │
                       │               RESOLVED ─────────────────────────┘
                       │               (terminal, WORM entry written)
                       └─────────────────────────────────────────────────┘
```

**State transitions:**

| Transition | Actor | Precondition | Effect |
|-----------|-------|-------------|--------|
| DRAFT → ACTIVE | CITADEL admin | Manual review complete | Gate 4 begins blocking |
| DRAFT → deleted | CITADEL admin | Advisory deemed invalid | No WORM entry; advisory removed |
| ACTIVE → EXPIRED | System (cron) | `expires_at` reached and not resolved | Gate 4 unblocked; WORM entry written |
| ACTIVE → RESOLVED | CITADEL admin | Admin confirms threat mitigated | Gate 4 unblocked; WORM entry written; `resolution_note` required |
| EXPIRED → RESOLVED | CITADEL admin | Post-expiry confirmation | Adds resolution note to WORM record |

**Rule:** An advisory in `RESOLVED` or `EXPIRED` state must never be reactivated. A new advisory
must be created instead. This preserves the immutability of the governance record.

**Rule:** Resolving an `ACTIVE` advisory requires `resolution_note` (minimum 20 characters). The
note is written to the WORM entry. This prevents silent advisory clearance.

### 4.3 MARSHAL Gate 4 Evaluation Contract

MARSHAL evaluates Gate 4 by querying AUGUR for active advisories that match both the Kerkese's
`project_id` and `action.type`:

```
Gate 4 blocks if:
  EXISTS advisory WHERE
    status = 'ACTIVE'
    AND severity = 'CRITICAL'
    AND (affects.projects = '*' OR project_id IN affects.projects)
    AND (affects.action_types = '*' OR action.type IN affects.action_types)
```

`HIGH` advisories do not block MARSHAL. They raise VIGIL to AMBER but permit operations to
proceed, producing a `WARN` annotation in the MARSHAL outcome's `reasons` field.

**MARSHAL outcome with active HIGH advisory (non-blocking):**

```json
{
  "outcome": "EXECUTE",
  "gates": [
    {"gate": 4, "name": "advisory", "status": "WARN",
     "detail": "1 HIGH advisory active for project ABISSNET_TCL_001 (advisory_id: uuid)"}
  ]
}
```

**MARSHAL outcome with active CRITICAL advisory (blocking):**

```json
{
  "outcome": "REFUSE",
  "gates": [
    {"gate": 4, "name": "advisory", "status": "FAIL",
     "detail": "CRITICAL advisory blocks 'deploy_change' for project ABISSNET_TCL_001 (advisory_id: uuid, title: 'Unpatched CVE-2026-XXXX...')"}
  ],
  "reasons": ["Gate 4 FAIL: CRITICAL advisory active — resolve advisory before proceeding"]
}
```

MARSHAL reads advisories from an in-process cache refreshed every 30 seconds. Maximum advisory
evaluation latency after activation: 30 seconds.

### 4.4 VIGIL Integration

AUGUR advisory state drives VIGIL health state:

| Advisory condition | VIGIL state |
|--------------------|------------|
| No active advisories | GREEN (advisory contribution) |
| ≥ 1 HIGH advisory, no CRITICAL | AMBER |
| ≥ 1 CRITICAL advisory | RED |

The `GET /api/v1/vigil/status` response includes the current advisory summary:

```json
{
  "active_advisories": [
    {
      "advisory_id": "uuid",
      "title": "...",
      "severity": "HIGH",
      "affects_projects": ["ABISSNET_TCL_001"],
      "affects_action_types": ["deploy_change"],
      "expires_at": "2026-04-07T09:00:00Z"
    }
  ]
}
```

### 4.5 AUGUR API Endpoints

```
POST   /api/v1/augur/advisories          Create advisory (status: DRAFT)
GET    /api/v1/augur/advisories          List advisories (filterable by status, severity, project)
GET    /api/v1/augur/advisories/{id}     Get advisory by ID
PATCH  /api/v1/augur/advisories/{id}     Activate, resolve, or update an advisory
DELETE /api/v1/augur/advisories/{id}     Delete a DRAFT advisory only

GET    /api/v1/augur/advisories/active   List ACTIVE advisories (used internally by MARSHAL)
```

**Activate advisory:**

```bash
PATCH /api/v1/augur/advisories/{id}
{"action": "activate"}
```

**Resolve advisory:**

```bash
PATCH /api/v1/augur/advisories/{id}
{"action": "resolve", "resolution_note": "CVE-2026-XXXX patched across all connectors in deploy 1.2.1"}
```

**Permissions:**

| Operation | Required permission |
|-----------|-------------------|
| Create, activate, resolve | `augur.admin` |
| Read (list, get) | `augur.read` |
| MARSHAL Gate 4 read | `augur.read` (connector key) |

### 4.6 WORM Entries for Advisory Transitions

Every advisory state transition writes a WORM entry via `POST /api/v1/worm/emit`:

```json
{
  "source": "augur",
  "event_type": "advisory.activated",
  "actor_user_id": 42,
  "project_id": null,
  "payload": {
    "advisory_id": "uuid",
    "title": "...",
    "severity": "CRITICAL",
    "affects": {"projects": ["*"], "action_types": ["deploy_change"]}
  }
}
```

Event types: `advisory.created`, `advisory.activated`, `advisory.resolved`, `advisory.expired`.

A MARSHAL evaluation that produces a Gate 4 FAIL does **not** write a separate WORM entry for
the advisory (the MARSHAL evaluation itself is already WORM-logged). The advisory WORM entries
cover the advisory lifecycle only.

## Alternatives Considered

### Inline Advisory Data in MARSHAL Evaluation Request

**Proposal:** Allow Kerkese submitters to assert "no relevant advisories" by including an
attestation in the request, avoiding the Gate 4 AUGUR query.

**Rejected because:** This would allow a Kerkese submitter to bypass CRITICAL advisories by
simply asserting they have checked and none apply. SoD requires that the entity evaluating the
advisory be independent of the entity requesting the action. AUGUR's server-side check is the
SoD-compliant path.

### Automatic Advisory Creation from CVE Feeds

**Proposal:** Connect AUGUR to a CVE/NVD feed and auto-create advisories for CVEs that affect
opensecstack dependencies.

**Deferred (not rejected):** Automated CVE ingestion is valuable but requires a mapping from CVE
entries to `affects.action_types`, which is non-trivial. This is tracked as a future AUGUR
enhancement. The current RFC specifies only the advisory schema and lifecycle; the ingestion
source is intentionally left pluggable via the `source: api_import` field.

## Impact

### Platforms Affected

| Platform | Impact |
|----------|--------|
| CITADEL | Implement `augur.advisories` table, API endpoints, Gate 4 integration |
| All platforms (MARSHAL callers) | No change to Kerkese schema; Gate 4 behaviour becomes deterministic |
| VIGIL | `active_advisories` field in status response now populated |

### Breaking Changes

None. Gate 4 was previously a stub returning PASS. This RFC makes Gate 4 functional. Existing
MARSHAL integrations will begin seeing Gate 4 FAIL/WARN outcomes once an advisory is created.
Operators should ensure no blocking CRITICAL advisories are active before deploying.

### Migration

No data migration required. The `augur.advisories` table is new; no existing data needs to be
moved.

---

## Open Questions

1. **Advisory deduplication.** If VIGIL_DEEP auto-creates an advisory for the same CVE that a
   human admin has already manually created, should the system merge them or create two separate
   records? Current proposal: create two records; operator merges manually via resolve + create.

2. **Advisory expiry default.** Should `expires_at` be mandatory for manually created advisories
   to prevent indefinite blocking? Proposal: require `expires_at` ≤ 90 days from activation;
   renewal creates a new advisory.

3. **Multi-severity advisory.** Can a single advisory have different severities for different
   action types (e.g., CRITICAL for `deploy_change` but HIGH for `config_update`)? Current
   design: one severity per advisory; use two advisories with different severities if needed.
