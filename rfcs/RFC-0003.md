# RFC-0003: WORM Long-Term Archival and Cold Storage

- **Status:** Draft
- **Priority:** Low
- **Date:** 2026-03-31
- **Authors:** Security Intelligence Group (SIG)
- **Depends on:** RFC-0001 (CITADEL Governance Protocol)

---

## Summary

This RFC specifies the long-term archival strategy for the CITADEL WORM audit log. It addresses
RFC-0001 Open Question 4 (retention for high-volume deployments) and defines the lifecycle
transitions from hot (live PostgreSQL) to warm (compressed on-disk archive) to cold (off-site,
tamper-evident storage), along with the verification procedure for archived entries.

---

## Motivation

NIS2 Article 21(2) and the associated implementing acts require essential and important entities
to retain security-relevant audit records for a minimum of seven years. The CITADEL WORM log
(`citadel.log`) is the authoritative audit record for the opensecstack governance layer. As
deployments scale, storing seven years of WORM entries in the primary PostgreSQL instance becomes
operationally expensive and risks performance degradation on the live chain.

RFC-0001 §3.3 acknowledges this problem:

> *"For high-volume deployments, the primary PostgreSQL store may grow large. The cold-storage
> archival format and verification procedure for archived entries needs a separate spec."*

This RFC provides that spec.

---

## Design

### 4.1 Storage Tiers

The WORM log uses three tiers of storage with defined transition criteria:

| Tier | Storage | Retention | Query access | Chain verifiable |
|------|---------|-----------|-------------|-----------------|
| **Hot** | Primary PostgreSQL (`citadel.log`) | 0–24 months | Full SQL, real-time | Yes (live chain) |
| **Warm** | Compressed archive on primary host filesystem | 24–36 months | Batch query via CLI | Yes (archive verification) |
| **Cold** | Off-site immutable object store (S3/compatible) or WORM tape | 36–84 months (7 years total) | Restore-on-demand | Yes (after restore) |

The hot tier is the live operational store. Warm and cold tiers are write-once on archive
creation; no further appends are permitted to an archived segment.

### 4.2 Archive Segment Format

WORM entries are archived in **segments**: non-overlapping, contiguous ranges of `log_id` values
bounded by chain anchor rotations. A segment is always aligned to anchor boundaries so the
chain hash can be verified independently without requiring adjacent segments.

**Segment naming convention:**

```
citadel-worm-<anchor_id_start>-<anchor_id_end>-<rotation_seq_start>-<rotation_seq_end>.tar.zst
```

Example:
```
citadel-worm-000001-000045-0000-0044.tar.zst
```

**Segment archive contents:**

```
citadel-worm-000001-000045-0000-0044.tar.zst
├── entries/
│   ├── 000001.jsonl        # WORM log entries, one JSON object per line
│   ├── 000002.jsonl
│   └── ...
├── anchors.json            # All chain_anchor records in this range
├── manifest.json           # Segment metadata and integrity digests
└── manifest.sig            # Ed25519 signature over manifest.json
```

**`manifest.json` schema:**

```json
{
  "schema_version": "1.0",
  "segment_id": "uuid",
  "created_at": "2026-03-31T02:00:00Z",
  "log_id_range": {"first": 1, "last": 45000},
  "anchor_range": {"first_anchor_id": 1, "last_anchor_id": 45, "rotation_seq": [0, 44]},
  "entry_count": 45000,
  "sha256_entries_dir": "e3b0c44298fc1c149afb...",
  "sha256_anchors_json": "a665a45920422f9d417e...",
  "signing_key_id": "uuid-of-ed25519-key"
}
```

`sha256_entries_dir` is the SHA-256 of the canonical concatenation of all per-file SHA-256
digests in `entries/`, in filename-lexicographic order, separated by newlines.

**`manifest.sig`:** Ed25519 signature over the UTF-8 bytes of `manifest.json`. The signing key
is a CITADEL-internal Ed25519 key pair; the public key is stored in `citadel.signing_keys` and
published to the out-of-band notary alongside each chain anchor.

### 4.3 Archive Creation Procedure

Archive creation is triggered automatically after each `PLAN`-type anchor rotation (every 30
days) and can be triggered on-demand:

```bash
POST /api/v1/worm/archive
{"anchor_id_range": {"from": 1, "to": 45}}   # optional; defaults to all unarchived segments
```

**Procedure (performed by CITADEL internally):**

```
1. Lock the log_id range for archival (no new entries may be written in range).
2. Export all citadel.log rows in range to JSONL files (one file per 1000 entries).
3. Export all chain_anchor rows in range to anchors.json.
4. Compute per-file SHA-256 digests and sha256_entries_dir.
5. Compose manifest.json.
6. Sign manifest.json with the CITADEL Ed25519 key → manifest.sig.
7. Pack as .tar.zst (zstd level 19 for maximum compression).
8. Verify archive integrity (unpack, re-verify sha256_entries_dir).
9. Write a WORM entry: event_type = 'worm.segment_archived', payload includes segment_id,
   sha256 of the .tar.zst file, and storage destination.
10. Move archive to warm tier (local filesystem path: $CITADEL_WARM_PATH).
11. Update citadel.archive_segments record with status = 'warm'.
```

Step 8 (integrity re-verify) is mandatory. Archive creation fails if the verification step
fails; the archive is discarded and an alert is raised.

### 4.4 Cold Tier Transition

Warm segments older than 36 months are moved to cold storage automatically:

```
1. Upload .tar.zst to configured cold storage target (S3/compatible or WORM tape).
2. Verify the uploaded copy matches the local SHA-256 (download + compare, or ETag match).
3. Deposit the manifest.json SHA-256 and the cold storage URL to the out-of-band notary.
4. Write a WORM entry: event_type = 'worm.segment_cold_tiered', payload includes storage URL
   and out-of-band notary reference.
5. Update citadel.archive_segments record with status = 'cold', cold_storage_url populated.
6. Delete local warm copy (only after step 2 and 4 are confirmed successful).
```

Cold storage must be configured with object lock / WORM policy (S3 Object Lock in COMPLIANCE
mode, or equivalent). CITADEL does not manage the cold storage WORM enforcement — it is the
operator's responsibility to configure the target storage as write-once.

### 4.5 Verification Procedure

**Warm/cold segment verification:**

```bash
citadel-worm verify --segment citadel-worm-000001-000045-0000-0044.tar.zst \
                    --public-key /etc/citadel/signing-key.pub

# Output:
# Segment: citadel-worm-000001-000045-0000-0044.tar.zst
# Entries:       45,000
# Anchor range:  1 → 45 (rotation_seq 0 → 44)
# Manifest SHA-256: e3b0c44298fc1c14...
# Signature:     VALID (key: uuid-of-ed25519-key)
# Entry digest:  PASS (sha256_entries_dir matches)
# Chain anchors: PASS (45 anchors verified, prev_anchor_hash chain intact)
# Result:        VERIFIED
```

**Full chain continuity verification (all tiers):**

```bash
citadel-worm verify-chain --from 2026-01-01 --to 2026-03-31 \
                           --hot-db postgresql://... \
                           --warm-path /mnt/citadel-warm \
                           --cold-index /etc/citadel/cold-index.json
```

This command:
1. Enumerates all archive segments and hot entries covering the requested date range.
2. Verifies each segment manifest signature.
3. Verifies that the last `chain_hash` of each segment matches the `prev_anchor_hash` of the
   first anchor in the next segment.
4. Verifies the hot tier chain from the last archived anchor to the current HEAD.
5. Reports any gaps, signature failures, or chain breaks.

### 4.6 `citadel.archive_segments` Table

```sql
CREATE TABLE citadel.archive_segments (
    segment_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    anchor_id_start     INTEGER NOT NULL REFERENCES citadel.chain_anchor(anchor_id),
    anchor_id_end       INTEGER NOT NULL REFERENCES citadel.chain_anchor(anchor_id),
    rotation_seq_start  INTEGER NOT NULL,
    rotation_seq_end    INTEGER NOT NULL,
    log_id_first        BIGINT NOT NULL,
    log_id_last         BIGINT NOT NULL,
    entry_count         INTEGER NOT NULL,
    archive_filename    TEXT NOT NULL,
    sha256_archive      CHAR(64) NOT NULL,
    manifest_sha256     CHAR(64) NOT NULL,
    signing_key_id      UUID NOT NULL,
    status              TEXT NOT NULL CHECK (status IN ('warm', 'cold', 'cold_verified')),
    warm_path           TEXT,
    cold_storage_url    TEXT,
    cold_notary_ref     TEXT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    cold_tiered_at      TIMESTAMPTZ
);
```

This table is NOT append-only (status transitions from `warm` → `cold` → `cold_verified` are
permitted). However, `log_id_first`, `log_id_last`, `sha256_archive`, and `manifest_sha256` are
immutable after INSERT and enforced by a trigger.

### 4.7 Hot Tier Pruning

After a segment is confirmed in cold storage (`status = 'cold_verified'`), CITADEL may prune
the corresponding entries from the hot PostgreSQL table. Pruning is:

- **Disabled by default.** Must be explicitly enabled in `citadel.yaml`:
  ```yaml
  archival:
    hot_prune_enabled: true
    hot_prune_min_cold_age_days: 180   # must be in cold ≥ 180 days before pruning
  ```
- **Partial:** Only entries where `ts_utc < NOW() - interval '36 months'` and whose segment
  has `status = 'cold_verified'` are eligible.
- **WORM-logged:** Each pruning batch writes a `worm.hot_pruned` entry listing the `log_id`
  range removed and the cold storage URL of the corresponding segment.
- **Irreversible:** Pruned rows cannot be recovered from the hot database; they must be restored
  from cold storage.

Pruning is a deliberate operational choice. Operators who want full hot-tier query access for
7 years can leave pruning disabled at the cost of storage growth.

## Alternatives Considered

### PostgreSQL Table Partitioning Without Archival

**Proposal:** Use PostgreSQL declarative partitioning by time, offloading old partitions to
cheaper tablespaces (e.g., ZFS compressed volumes), without a separate archive format.

**Rejected because:** PostgreSQL tablespaces do not provide the tamper-evidence or off-site
guarantees required by NIS2. A DBA with tablespace access can modify or delete old partition
files without any cryptographic trace. The tar.zst format with Ed25519 signature and notary
deposit is the only architecture that provides cryptographic proof of record integrity
independent of the database engine.

### Continuous Streaming to Object Storage (No Warm Tier)

**Proposal:** Stream every WORM entry directly to S3/compatible cold storage at write time,
eliminating the warm tier.

**Rejected because:** Continuous streaming couples the WORM write path to the availability of
the cold storage target. RFC-0001 requires the WORM entry to be written *before* the HTTP
response is returned; any cold storage latency would propagate directly to MARSHAL response
times. The hot + warm + cold tiering keeps the write path strictly local.

### PostgreSQL Logical Replication to a Read-Only Replica for Archival

**Proposal:** Use Postgres logical replication to maintain a replica that is never pruned, acting
as the long-term store.

**Deferred:** A replication replica can serve as a backup but does not satisfy the out-of-band
tamper-evidence requirement (a replica is under the same administrative domain). It can
complement the archival strategy but does not replace it.

## Impact

### Platforms Affected

| Platform | Impact |
|----------|--------|
| CITADEL | Implement archival job, `archive_segments` table, `citadel-worm` CLI tool |
| All platforms (MARSHAL callers) | No impact on API contracts |
| Operators | Must configure `CITADEL_WARM_PATH` and cold storage credentials |

### Breaking Changes

None. Hot-tier entries remain queryable via existing APIs until pruning is enabled. The archive
format is additive.

### New Operator Requirements

| Variable | Description |
|----------|-------------|
| `CITADEL_WARM_PATH` | Filesystem path for warm-tier segment archives |
| `CITADEL_COLD_BUCKET` | S3-compatible bucket URL for cold tier |
| `CITADEL_COLD_CREDENTIALS` | Credentials file/ARN for cold bucket access |
| `CITADEL_SIGNING_KEY_PATH` | Path to Ed25519 private key PEM for manifest signing |
| `CITADEL_SIGNING_KEY_PUBLIC` | Corresponding public key (distributed to auditors) |

## Open Questions

1. **Signing key rotation.** Ed25519 signing keys should be rotated periodically. How are old
   signing keys kept accessible for verification of archives signed with them? Proposal: retain
   all historical public keys in `citadel.signing_keys`; the manifest includes `signing_key_id`
   so verifiers know which public key to use.

2. **Restore API.** Should CITADEL expose a `POST /api/v1/worm/restore` endpoint to re-hydrate
   cold entries into the hot tier for audit queries, or should restores be a purely CLI/operator
   operation? Current proposal: CLI only, to avoid adding an authenticated restore path that
   could be abused.

3. **Segment size tuning.** The anchor rotation period (currently 30 days) determines segment
   size. For deployments with very high event rates (> 1M entries/day), 30-day segments may
   produce archives too large for efficient transfer. Should the segment boundary be configurable
   independently of the anchor rotation schedule?
